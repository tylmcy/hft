🧵 线程工作模型数据流图 V2

⚠️ V2 重要变更
1. Order Queue 和 Cancel Queue 合并 - 统一为 Order Queue，包含 NEW_ORDER 和 CANCEL_ORDER 两种类型
2. ClearingWorker 按 AccountId 分片 - 同一账户的操作在同一线程串行化，减少 compute 调用
3. MatchingEngine 支持多 Symbol - 单线程处理所有 Symbol，每个 Symbol 独立 OrderBook
4. OrderBook 持久化到 Chronicle Map - orderbook.dat 存储所有挂单状态，重启后恢复
📊 流程 1: HTTP请求 → 订单处理 (同步路径)
1
Tomcat HTTP-IO Thread (8-32线程)
接收 HTTP POST /api/orders 请求
不访问 Chronicle Map
2
Tomcat HTTP-IO Thread (同一线程)
参数校验 → 风控检查 (读 Chronicle Map)
读取: accounts.dat, positions.dat
3
Tomcat HTTP-IO Thread (同一线程)
compute 原子冻结资金/持仓
写入: accounts.dat, positions.dat (compute原子操作)
4
Tomcat HTTP-IO Thread (同一线程)
写入订单到 Order Queue (类型: NEW_ORDER)
写入: order_queue.dat (Chronicle Queue)
5
Tomcat HTTP-IO Thread (同一线程)
同步返回 OrderResult 给客户端
响应: orderId, status="PENDING"
❌ 流程 2: 撤单请求 (写入 Order Queue)
1
Tomcat HTTP-IO Thread
接收 HTTP DELETE /api/orders/{orderId}
不访问 Chronicle Map
2
Tomcat HTTP-IO Thread
写入撤单请求到 Order Queue (类型: CANCEL_ORDER)
写入: order_queue.dat (Chronicle Queue)
3
Tomcat HTTP-IO Thread
同步返回 CancelResult (已提交)
响应: orderId, status="CANCEL_PENDING"
✅ 统一的 Order Queue 设计
Order Queue 包含两种事件类型: NEW_ORDER 和 CANCEL_ORDER
MatchingEngine 统一处理，保证顺序
无需独立的 Cancel Queue 和 CancelProcessor 线程
⚡ 流程 3: 订单 → 撮合 (多 Symbol 支持)
1
MatchingEngine Thread (单线程)
从 Order Queue 零拷贝读取 OrderEvent
读取: order_queue.dat (ExcerptTailer)
2
MatchingEngine Thread (同一线程)
根据 symbol 获取对应的 OrderBook
内存: Map<String, OrderBook> orderBooks
3a
MatchingEngine Thread (NEW_ORDER)
写入 orderbook.dat → 加入 OrderBook → 执行撮合
写入: orderbook.dat (PENDING状态) → 内存 OrderBook
3b
MatchingEngine Thread (CANCEL_ORDER)
从 OrderBook 移除 → 更新 orderbook.dat 状态
写入: orderbook.dat (CANCEL状态) → 生成 CancelEvent
4
MatchingEngine Thread (同一线程)
生成 TradeEvent / CancelEvent，写入 Trade Queue
写入: trade_queue.dat (Chronicle Queue)
5
MatchingEngine Thread (同一线程)
更新 orderbook.dat (remainingQty, status)
写入: orderbook.dat (compute 原子更新)
📊 多 Symbol OrderBook 结构
symbol → OrderBook 每个 Symbol 独立的 OrderBook，内存 TreeMap 结构
买单: 价格降序 最高价优先成交
卖单: 价格升序 最低价优先成交
撮合算法: 价格优先、时间优先
💰 流程 4: 成交 → 清算 (单线程顺序处理)
1
ClearingWorker Thread (单线程)
从 Trade Queue 读取 TradeEvent
读取: trade_queue.dat (ExcerptTailer)
2
ClearingWorker Thread (同一线程)
putIfAbsent 幂等检查 (防止重复清算)
原子操作: processed_trades.dat (putIfAbsent)
3
ClearingWorker Thread (同一线程)
compute 原子更新买方账户/持仓
写入: accounts.dat, positions.dat (compute)
4
ClearingWorker Thread (同一线程)
compute 原子更新卖方账户/持仓
写入: accounts.dat, positions.dat (compute)
5
ClearingWorker Thread (同一线程)
更新 Index (单线程，直接赋值)
写入: progress.dat (直接 setIndex)
6
ClearingWorker Thread (同一线程)
推送 WebSocket 成交通知
写入: WebSocket Channel (Netty异步发送)
7
ClearingWorker Thread (同一线程)
继续处理下一个成交 (循环)
无内存队列，直接从 Trade Queue 读取
🔑 单线程清算优势
Index 顺序更新 无冲突，无需滑动窗口
设计简单 无内存队列，无多线程同步问题
重启恢复简单 从 Index + 1 开始读取即可
性能足够 每笔清算 ~5-10μs，10万 TPS
🔓 流程 5: 撤单解冻 (MatchingEngine 处理)
1
MatchingEngine Thread
从 Order Queue 读取 CANCEL_ORDER 类型
读取: order_queue.dat
2
MatchingEngine Thread
从 OrderBook 移除订单，更新 orderbook.dat
写入: orderbook.dat (status=CANCEL)
3
MatchingEngine Thread
生成 CancelEvent，写入 Trade Queue
写入: trade_queue.dat
4
ClearingWorker Thread (单线程)
读取 CancelEvent，compute 原子解冻资金/持仓
写入: accounts.dat, positions.dat (compute)
5
ClearingWorker Thread
推送 WebSocket 撤单结果
写入: WebSocket Channel
🔄 JVM 重启恢复流程
1
Main Thread (启动线程)
加载所有 Chronicle Map 文件
读取: accounts.dat, positions.dat, orderbook.dat, progress.dat, processed_trades.dat
2
Main Thread
从 orderbook.dat 恢复所有 Symbol 的 OrderBook
读取: orderbook.dat → 重建 Map<String, OrderBook>
3
Main Thread
读取各队列的 Index
读取: progress.dat.get("order_queue_index"), progress.dat.get("trade_queue_index")
4
MatchingEngine Thread
从 order_queue_index + 1 开始读取
tailer.moveToIndex(orderIndex + 1)
5
TradeReader Thread
从 trade_queue_index + 1 开始读取
tailer.moveToIndex(tradeIndex + 1)
6
ClearingWorker Thread
putIfAbsent 幂等检查 (防止重复清算)
如果已处理，跳过；否则执行清算
7
ClearingWorker Thread
标记 Index 已处理，滑动窗口向前移动
更新: progress.dat (BitSet + windowStart)
📊 OrderBook 恢复流程
orderbook.dat 结构 Key: (symbolCode << 32) | orderId, Value: OrderState
恢复时遍历所有 OrderState，按 symbol 分组重建 OrderBook
只恢复 PENDING 和 PARTIAL_FILLED 状态的订单
FILLED 和 CANCEL 状态的订单跳过
🔒 防重复清算保证 (单线程)
tradeId 去重 putIfAbsent 在清算前执行，防止重复清算
Index 顺序更新 单线程保证 Index 顺序，无需滑动窗口
重启后可能重复读取，但不会重复处理
putIfAbsent 在清算前执行，保证原子性

💾 Chronicle Map 存储结构 (V2)
账户/持仓存储
accounts.dat Key: accountId, Value: AccountState (balance, available, frozen, margin)
positions.dat Key: (accountId << 32) | symbolCode, Value: PositionState
订单簿存储 (新增)
orderbook.dat Key: (symbolCode << 32) | orderId, Value: OrderState
OrderState: orderId, symbol, price, quantity, remainingQty, side, accountId, status, createTime, updateTime
status: PENDING / PARTIAL_FILLED / FILLED / CANCEL
进度/幂等存储
progress.dat Key: "order_queue_index" / "trade_queue_index" / "persistence_index"
processed_trades.dat Key: tradeId, Value: ProcessedTradeState (幂等去重)
