⚠ V12 Important Changes
1 JVM内存为主存储 -- ConcurrentHashMap存储账户/持仓/订单，Chronicle Map仅用于快照持久化
2 单线程Worker批量处理 -- AccountWorker/MatchingEngine/ClearingWorker各单线程，批量处理提升吞吐
3 五个CQ事件队列 -- account_input, account_output, matching_input, matching_output, account_settlement
4 SNAPSHOT事件触发快照 -- SnapshotWorker写入SNAPSHOT事件到CQ，Worker处理时先处理同批普通事件再快照
5 三层幂等模型 -- HTTP层idempotencyKey → MatchingEngine processed_order_ids → AccountWorker processed_trade_ids
6 四阶段恢复 -- AccountWorker → MatchingEngine → ClearingWorker → AccountWorker第二阶段
7 CompletableFuture同步 -- HTTP下单使用 CompletableFuture.orTimeout(5s) 等待冻结完成
8 RPO = 0 -- CQ writeMode=SYNC持久化，快照原子rename+MD5校验，重启后数据零丢失

System Overview -- Thread & CQ Topology

Flow 1: HTTP Order Request (Synchronous Path)

1 HTTP POST /api/orders -- Synchronous Freeze SYNC
1
Tomcat Virtual Thread HTTP
Receive HTTP POST /api/orders request
2
Tomcat Virtual Thread VALIDATE
Parameter validation → Trading phase check (volatile read) → Price limit check → Idempotent check (idempotencyKey)
Layer 1: HTTP idempotencyKey
3
Tomcat Virtual Thread WRITE CQ
Generate orderId (Snowflake) → Create CompletableFuture → Write account_input CQ (NEW_ORDER)
account_input.cq4
4
Tomcat Virtual Thread WAIT
future.orTimeout(5, TimeUnit.SECONDS) -- Block virtual thread until AccountWorker completes freeze
Returns orderId + status=PENDING on success, or TimeoutException on failure
CompletableFuture Synchronization
HTTP thread writes NEW_ORDER to account_input.cq4 with attached CompletableFuture
Virtual thread blocks on future.orTimeout(5s) -- lightweight parking, no OS thread waste
AccountWorker batch-completes all futures after processing: future.complete(result)
Timeout → order may still be processed; consistency guaranteed by idempotency

Flow 2: AccountWorker Batch Processing (Phase 2)

2 AccountWorker -- Freeze/Unfreeze/Settle/Deposit 1 THREAD BATCH 50
1
AccountWorker Thread READ BATCH
Batch read from account_input CQ (max 50 events, wait 1ms)
account_input.cq4
2
AccountWorker Thread PROCESS
Batch process events by type:
• INSTRUMENT_INIT: Store into InstrumentStore
• PHASE_CHANGE: Update currentPhase volatile variable
• DEPOSIT: balance += amount, available += amount
• NEW_ORDER: Freeze funds/position (ConcurrentHashMap in-memory):
Market buy: frozen = limit_price x qty + commission(ceil)
Limit buy: frozen = price x qty + commission(ceil)
Sell: freeze position quantity
3
AccountWorker Thread PENDING-MUTATIONS
Delayed apply pattern -- collect mutations to pending-mutations, apply only after CQ write succeeds
If CQ write fails, mutations are discarded; guarantees consistency between memory and CQ
4
AccountWorker Thread WRITE CQ
Batch write to matching_input CQ + account_output CQ
matching_input.cq4 account_output.cq4
5
AccountWorker Thread COMPLETE
Batch CompletableFuture.complete() + WebSocket push (order_update, account_update)
Account Invariants
balance == available + frozen
frozen == marginFrozen + orderFrozen
|position.quantity| == available + frozen + t1Locked
Single-threaded processing guarantees no concurrent modification -- no locking on ConcurrentHashMap needed

Flow 3: MatchingEngine Batch Matching (Phase 3)

3 MatchingEngine -- Price-Time Priority Matching 1 THREAD BATCH 50
1
MatchingEngine Thread READ BATCH
Batch read from matching_input CQ (max 50 events, wait 1ms)
matching_input.cq4
2
MatchingEngine Thread GROUP
Group events by symbol for sequential processing per symbol
3
MatchingEngine Thread MATCH
Process events by type:
• INSTRUMENT_INIT: Store into memory
• NEW_ORDER: Idempotent check (processed_order_ids) → Phase check (volatile) → Add to OrderBook → Match
LIMIT: Price-time priority; unfilled stays in OrderBook
MARKET: Match with best counterparty; unfilled immediately cancelled (CANCEL_SUCCESS)
FAK: Fill what can be filled at limit price, cancel remainder
FOK: All-or-nothing; if fillable_qty < quantity, cancel entire order
• CANCEL_ORDER: Remove from OrderBook → CANCEL_SUCCESS / CANCEL_REJECT
Layer 2: processed_order_ids
4
MatchingEngine Thread WRITE CQ
Batch write to matching_output CQ -- TRADE events MUST precede CANCEL_SUCCESS in same batch
matching_output.cq4
5
MatchingEngine Thread MARKET DATA
Five-level quote push (every 3s) + K-line update (real-time)
Order Type Matching Rules
LIMIT -- Price priority first, then time priority; unfilled remains in OrderBook
MARKET -- Match with best counterparty immediately; unfilled portion cancelled (CANCEL_SUCCESS)
FAK (Fill and Kill) -- Fill what's available at limit price, cancel the rest
FOK (Fill or Kill) -- If entire quantity cannot be filled, cancel the entire order
TRADE events are always written before CANCEL_SUCCESS in the same batch to maintain causal order

Flow 4: ClearingWorker Batch Clearing (Phase 4)

4 ClearingWorker -- Commission Calculation & Settlement Event Generation 1 THREAD BATCH 100
1
ClearingWorker Thread READ BATCH
Batch read from matching_output CQ (max 100 events, wait 1ms)
matching_output.cq4
2
ClearingWorker Thread PROCESS
Process events by type:
• ORDER_UPDATE(status=NEW): Update order PENDING→NEW, WebSocket push
• TRADE: Update buy/sell filledQuantity → Calculate commission(floor) → Calculate frozenAmountUsed(ceil) → Generate SETTLEMENT x 2 → Write account_settlement CQ
• CANCEL_SUCCESS: Generate UNFREEZE → Write account_settlement CQ
• CANCEL_REJECT(PENDING_ORDER_NOT_IN_ORDERBOOK): If order status is PENDING/NEW → Generate UNFREEZE
3
ClearingWorker Thread NOTE
No idempotency check in ClearingWorker -- idempotency is guaranteed by AccountWorker downstream
Layer 3: AccountWorker processed_trade_ids
Commission & Frozen Amount Rounding
Commission: floor() -- rounded down, customer-friendly
Frozen amount used: ceil() -- rounded up, ensures sufficient frozen funds for settlement
Difference between frozen and used = refund to available
Each TRADE generates 2 SETTLEMENT events: one for buyer, one for seller

Flow 5: AccountWorker Settlement & Unfreeze

5 AccountWorker -- Settlement Transfer & Unfreeze (Same Thread) 1 THREAD
1
AccountWorker Thread READ
Batch read from account_settlement CQ
account_settlement.cq4
2
AccountWorker Thread SETTLE
Process SETTLEMENT:
• Idempotent check: settlementId = tradeId + "_" + orderId
• Buyer: frozen -= frozenAmountUsed, balance -= total_deduction, available += refund, position.quantity += qty, position.t1Locked += qty
• Seller: position.frozen -= qty, position.quantity -= qty, balance += net_income, available += net_income
• Verify invariant: balance == available + frozen
Layer 3: processed_trade_ids
3
AccountWorker Thread UNFREEZE
Process UNFREEZE:
• Idempotent check: unfreezeId = orderId
• Buy order: available += unfreezeAmount, frozen -= unfreezeAmount, orderFrozen -= unfreezeAmount
• Sell order: position.available += unfreezeQty, position.frozen -= unfreezeQty
4
AccountWorker Thread OUTPUT
Batch write to account_output CQ → WebSocket push (position_update, account_update)
account_output.cq4

Flow 6: Cancel Order Full Path

6 Cancel Order -- Cross-Thread Lifecycle ASYNC
1
HTTP Virtual Thread HTTP
Validate orderId → Write CANCEL_ORDER to account_input CQ → Return PENDING_CANCEL
2
AccountWorker Thread FORWARD
All CANCEL_ORDER events forwarded directly to matching_input CQ (no freeze/unfreeze in this phase)
3
MatchingEngine Thread REMOVE
Order in OrderBook → Remove → CANCEL_SUCCESS; Order not in OrderBook → CANCEL_REJECT
4
ClearingWorker Thread GENERATE
CANCEL_SUCCESS → Generate UNFREEZE → Write to account_settlement CQ
5
AccountWorker Thread UNFREEZE
Unfreeze funds/position → Update order status to CANCELLED → WebSocket push
Cancel Order Design Notes
Cancel requests go through the same CQ pipeline as new orders -- guarantees ordering
AccountWorker does NOT unfreeze on CANCEL_ORDER -- unfreeze only happens after CANCEL_SUCCESS from MatchingEngine
CANCEL_REJECT(PENDING_ORDER_NOT_IN_ORDERBOOK): if order is still PENDING/NEW, generate UNFREEZE to release frozen funds

Flow 7: Four-Phase Recovery Process

7 JVM Restart Recovery -- RPO = 0 Guaranteed RPO=0
1
AccountWorker Phase 1 SNAPSHOT + REPLAY
Load H2 Instrument data → Load account_snapshot_{idx}.dat + .checksum (MD5 verify) → Generate idempotent set → replay_mode = true → Replay account_input CQ from index+1
account_snapshot_{account_input_cq_index}.dat
2
MatchingEngine SNAPSHOT + REPLAY
Load matching_snapshot_{idx}.dat + .checksum (MD5 verify) → Restore OrderBook (TreeMap) → Generate idempotent set (processed_order_ids) → replay_mode = true → Replay matching_input CQ from index+1
matching_snapshot_{matching_input_cq_index}.dat
3
ClearingWorker POSITION + REPLAY
Read clearing_position.dat → Roll back matching_output to last processed index → Replay matching_output CQ (no idempotency check)
clearing_position.dat
4
AccountWorker Phase 2 SETTLEMENT REPLAY
Generate idempotent set (processed_trade_ids) → Replay account_settlement CQ → Settlement transfer + unfreeze (idempotent)
RPO = 0 Guarantee Mechanism
CQ writeMode=SYNC: every write is fsync'd to disk before acknowledgment
Snapshot files use atomic rename: write to .tmp → rename to final name
Each snapshot has a companion .checksum file with MD5 hash for integrity verification
Recovery replays from snapshot index + 1 through all remaining CQ events
Idempotent processing during replay prevents double-application of events

Three-Layer Idempotency Model

Layer 1: HTTP Idempotency Key
idempotencyKey
HTTP Request Layer
Client-generated unique key per request
Prevents duplicate HTTP submissions
Checked before writing to CQ
Layer 2: MatchingEngine processed_order_ids
processed_order_ids
MatchingEngine Layer
Set of order IDs already processed
Prevents duplicate order matching during replay
Stale entries evicted on snapshot
Layer 3: AccountWorker processed_trade_ids
processed_trade_ids / settlementId / unfreezeId
AccountWorker Layer
settlementId = tradeId + "_" + orderId
unfreezeId = orderId
Prevents duplicate settlement/unfreeze
Ultimate consistency guarantee
