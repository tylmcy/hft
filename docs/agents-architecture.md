# Agent 架构设计文档

> 版本: v1.0 | 日期: 2026-06-23 | 状态: **设计提案**
> 基于技术方案 V12.5，面向资深工程师评审

---

## 1. 背景与问题

当前系统聚焦于交易核心链路（下单 → 撮合 → 清算 → 结算），在以下几个方向上存在能力空白：

| 方向 | 现状 | 问题 |
|------|------|------|
| **做市商策略** | 架构预留了做市商用户入口（OpenAPI），但无内置策略运行支持 | 做市商需要一套可编程的策略框架来管理报价、库存和风险 |
| **数据一致性** | 系统承诺 RPO=0 和账户不变式（balance = available + frozen），但无运行时校验 | 约束只在代码层面隐含保证，缺乏独立验证 |
| **运维诊断** | AlertService 仅写日志，无延迟分析、堆积检测、根因定位能力 | 100K TPS / P99 <15ms 的目标缺乏持续监控 |
| **用户交互** | 下单/查询全部走 REST API，风格单一 | 部分操作（查持仓、查流水）用自然语言或引导式交互更高效 |
| **策略回测** | CQ 事件流天然可重放，但无重放引擎 | 历史数据沉淀在 CQ 和 H2 中，无利用手段 |
| **交易报告** | EOD 流程生成日终报告，但仅有关闭时的一次性输出 | 用户缺少按需生成交易分析的能力 |

Agent 架构的定位是**填补这些空白，且不侵入交易核心链路**。

---

## 2. 设计原则

| 原则 | 说明 |
|------|------|
| **与核心链路解耦** | 所有 Agent 不运行在 AccountWorker / MatchingEngine / ClearingWorker 的线程上，不共享内存数据结构的写路径。Agent 只能通过 REST API 或 WebSocket 订阅与系统交互 |
| **规则引擎兜底** | 每个 Agent 的核心逻辑用代码实现，AI 作为增强层。Agent 输出有格式约束和边界校验，越界则回退到保守默认值 |
| **可观测性优先** | Agent 自身的行为（触发、决策、结果）可审计、可追踪。Agent 不影响系统吞吐量目标 |
| **渐进式落地** | 每个 Agent 可独立实现，不依赖其他 Agent。从离线/旁路 Agent 开始，逐步扩展到在线辅助 |

### 3.1 与现有系统的通信方式

| 方式 | 方向 | 用途 |
|------|------|------|
| REST API | Agent → 系统 | 下单、撤单、查询账户/持仓/订单（做市商 Agent、智能客服 Agent） |
| WebSocket 订阅 | Agent → 系统 | 订阅订单簿、行情、订单更新、成交推送（做市商 Agent） |
| 内存旁路读 | Agent → 内存 | 只读访问 InMemoryAccountStore / InMemoryOrderStore / InMemoryPositionStore（一致性审计 Agent） |
| CQ 读 | Agent → CQ 文件 | 读取已持久化的事件流（策略回测 Agent、一致性审计 Agent） |
| H2 读 | Agent → H2 数据库 | 读取历史成交、资金流水（策略回测 Agent、交易报告 Agent） |
| AgentWebSocket | Agent → 前端 | Agent 的分析结果、告警、报告推送到前端页面 |

### 3.2 Agent 公共基础设施

| 组件 | 职责 | 现有系统复用 |
|------|------|-------------|
| **AgentContext** | 持有 SystemStatus + TradingPhase 的快照，各 Agent 通过它感知交易时段和系统状态，避免在不恰当的阶段运行 | 订阅 LifecycleManager.systemStatus 和 PhaseManager.currentPhase |
| **OutputValidator** | 校验 Agent 输出的格式和边界。参数越界时回退到保守默认值，非结构化输出走不到下游 | 新建组件 |
| **AgentLogger** | 每个 Agent 独立日志文件，记录触发时间、输入摘要、输出内容、降级事件 | 基于现有 logback，按 Agent 名路由 |
| **AgentWebSocket** | 扩展 WebSocket 通道类型，新增 `agent_alert`、`agent_report`、`agent_analysis` 通道 | 复用现有 Netty WebSocket 架构，WebSocketPushService 增加 Agent 相关推送方法 |

## 4. Agent 详细设计

### 4.1 做市商策略 Agent

#### 定位

当前系统在架构中预留了"做市商策略用户"的概念（通过 OpenAPI 接入，独立 JVM），但仅限于外部接入的设想。做市商策略 Agent 在系统内部实现一个可配置的策略运行引擎，使系统具备**内生做市能力**。

#### 与现有系统的差异对比

| 维度 | 现有系统 | 引入 Agent 后 |
|------|---------|-------------|
| 做市商接入 | 预留 OpenAPI，未实现 | 内置策略引擎，通过 WebSocket 对接订单簿 |
| 报价方式 | 用户手动下单 | 策略自动报价（固定价差/动态价差） |
| 库存管理 | 无自动库存管理 | 库存感知净值调整，净持仓上限保护 |
| 风险控制 | 无盘中自动风控 | 实时计算持仓敞口，越界自动停止报价 |

#### 设计

做市商 Agent 运行时架构：

```
                     ┌──────────────────────────────────────────────────────┐
                     │              做市商策略 Agent                         │
                     │                                                      │
                     │  ┌────────────┐  ┌──────────────┐  ┌────────────┐  │
                     │  │ 订单簿监听  │  │ 策略参数管理  │  │ 报价执行器  │  │
                     │  │ (WebSocket  │  │ • 固定价差   │  │ (REST API  │  │
                     │  │  订阅)      │  │ • 动态价差   │  │  下单/撤单) │  │
                     │  └──────┬─────┘  │ • 库存目标   │  └──────┬─────┘  │
                     │         │        │ • 最大敞口   │         │        │
                     │         │        └──────┬───────┘         │        │
                     │         ▼               │                 ▼        │
                     │  ┌───────────────────────────────────────────────┐  │
                     │  │          策略决策引擎（规则优先）               │  │
                     │  │  1. Bid/Ask 价格计算：参考价 ± 价差            │  │
                     │  │  2. 库存平衡：净持仓偏离目标时调整价差方向       │  │
                     │  │  3. 风险检查：净持仓上限、最大亏损、单笔金额      │  │
                     │  │  4. 报价生命周期：超时撤单、更新报价             │  │
                     │  └───────────────────────────────────────────────┘  │
                     │                                                      │
                     │  策略参数来源：                                       │
                     │  ┌──────────────┐    ┌──────────────────────────┐   │
                     │  │ 预定义模板    │    │ AI 策略调优（增强层）      │   │
                     │  │ (JSON配置)   │    │ • 每15分钟分析盘口形态     │   │
                     │  │ 价差范围     │───►│ • 建议价差调整方向         │   │
                     │  │ 库存目标     │    │ • 输出经过 OutputValidator │   │
                     │  │ 风控限额     │    │ • 越界回退到预定义模板值    │   │
                     │  └──────────────┘    └──────────────────────────┘   │
                     └──────────────────────────────────────────────────────┘
```

**策略模板示例**（JSON 配置，策略管理员预设）：

```json
{
  "symbols": ["600000", "000001"],
  "mode": "DYNAMIC_SPREAD",
  "spreadConfig": {
    "baseBps": 3,
    "minBps": 1,
    "maxBps": 10,
    "inventoryAdjustFactor": 0.5
  },
  "inventoryConfig": {
    "targetPerSymbol": 0,
    "maxNetExposure": 100000,
    "rebalanceThreshold": 20000
  },
  "riskConfig": {
    "maxOrderAmount": 500000,
    "maxDailyLoss": 100000,
    "maxPositionPerSymbol": 50000
  },
  "orderLifecycleMs": 10000
}
```

#### 降级路径

| 场景 | 行为 |
|------|------|
| AI 调优不可用（超时/异常） | 使用预定义模板的默认参数，继续规则引擎报价 |
| WebSocket 断开 | 清除所有已报订单，停止报价，定时重连 |
| 系统非 CONTINUOUS_TRADING | AgentContext 感知交易阶段，自动暂停报价 |
| 累计亏损超限 | 强制停止所有报价，标记策略为 HALTED，需管理员手动恢复 |

#### 数据流

```
WebSocket 订单簿推送 → [Agent] 策略决策引擎 → REST API 下单/撤单
                                          ↓
                                  AgentLogger（记录每笔决策）
```

#### 对系统性能的影响

做市商策略 Agent 通过 REST API 和 WebSocket 交互，与普通用户站在同一接口层。Agent 的报价频率取决于策略配置（典型值 3-10 秒/轮），远低于系统峰值吞吐，不构成性能风险。

### 4.2 一致性审计 Agent

#### 定位

系统在设计中明确承诺了数据一致性约束（RPO=0、账户不变式、持仓不变式），但这些约束在运行时没有被独立验证。一致性审计 Agent 作为**独立的只读审计者**，持续验证内存状态是否满足设计承诺。

#### 与现有系统的差异对比

| 维度 | 现有系统 | 引入 Agent 后 |
|------|---------|-------------|
| 账户不变式验证 | 仅代码隐含保证 | 运行时定时扫描，逐账户校验 `balance = available + frozen` |
| 持仓不变式验证 | 仅代码隐含保证 | 运行时定时扫描，逐持仓校验 `|quantity| = available + frozen + t1Locked` |
| 孤立冻结检测 | EOD 期间做一次 | 常态化运行，盘中即可发现异常 |
| 幂等集合一致性 | 无交叉校验 | 对比 trade_id 去重集合与 CQ 事件流，发现遗漏或重复 |
| 快照恢复验证 | 恢复流程自行完成 | 恢复完成后独立验证：快照加载值 + CQ 重放值 = 最终内存值 |
| 报告方式 | 无 | 审计结果通过 AgentWebSocket 推送，异常时 AlertService P0 告警 |

#### 设计

```
                     ┌──────────────────────────────────────────────────────┐
                     │              一致性审计 Agent                          │
                     │                                                      │
                     │  调度周期：每 30 秒（可配置）                          │
                     │                                                      │
                     │  ┌────────────────────────────────────────────────┐  │
                     │  │             审计执行器                           │  │
                     │  │                                                │  │
                     │  │  1. 账户审计                                    │  │
                     │  │     for each account:                           │  │
                     │  │       check: balance == available + frozen      │  │
                     │  │       check: frozen == marginFrozen + orderFrozen│  │
                     │  │       check: available >= 0, frozen >= 0        │  │
                     │  │       check: status consistency with balance    │  │
                     │  │                                                │  │
                     │  │  2. 持仓审计                                    │  │
                     │  │     for each position:                          │  │
                     │  │       check: |quantity| == avail + frozen + t1  │  │
                     │  │       check: available >= 0, frozen >= 0        │  │
                     │  │                                                │  │
                     │  │  3. 活跃订单审计                                  │  │
                     │  │     for each active order:                      │  │
                     │  │       check: account has matching frozen         │  │
                     │  │       check: order exists in InMemoryOrderStore  │  │
                     │  │                                                │  │
                     │  │  4. CQ 事件流审计（增量模式）                     │  │
                     │  │     上次审计位置 → 当前 CQ 最新位置               │  │
                     │  │     验证无未处理的事件堆积                        │  │
                     │  └────────────────────────────────────────────────┘  │
                     │                                                      │
                     │  结果处理：                                           │
                     │  ┌──────────┐  ┌──────────────┐  ┌───────────────┐  │
                     │  │ 全部通过  │  │  P2 告警     │  │  P0/P1 告警   │  │
                     │  │ → 静默   │  │ (小偏差)     │  │ (严重偏差)    │  │
                     │  └──────────┘  │ → 记录日志   │  │ → AlertService│  │
                     │                │ → 推送审计报告│  │ → 推送审计报告 │  │
                     │                └──────────────┘  │ → 建议处理方案 │  │
                     │                                  └───────────────┘  │
                     └──────────────────────────────────────────────────────┘
```

#### 关键设计决策

- **只读旁路**：审计 Agent 读内存时不持有锁，对 Worker 线程零影响。审计读取的是某一刻的快照视图，不要求与 Worker 精确同步——微小的时间差偏差通过阈值容忍
- **阈值容忍**：允许 `balance - (available + frozen)` 在短时间内非零且持续缩小，视为正常（CQ 事件正在传输中）。只有连续两次扫描均超阈值才告警
- **审计上下文独立**：审计 Agent 不修改任何数据，不做修复。修复由人工或独立的修复流程处理

#### 降级路径

| 场景 | 行为 |
|------|------|
| 审计 Agent 自身异常 | 不影响核心交易链路，仅跳过本次审计周期 |
| 系统处于 RECOVERING / SNAPSHOTTING 状态 | AgentContext 感知后暂停审计 |
| 审计发现大量偏差 | 按账户/品种逐个告警，不做批量冲击，避免告警风暴 |

### 4.3 智能客服 Agent

#### 定位

当前系统的所有操作都通过 REST API 完成，用户需要了解 API 语义才能完成查询和下单。智能客服 Agent 提供一个**自然语言交互界面**，将用户的日常问询转化为系统调用。

#### 与现有系统的差异对比

| 维度 | 现有系统 | 引入 Agent 后 |
|------|---------|-------------|
| 查询方式 | 点击页面/调 API | 自然语言："查一下 600000"、"我的账户还有多少钱" |
| 操作流程 | 表单式下单 | 对话式引导："买入 200 股浦发银行" → 确认 → 执行 |
| 用户入口 | REST API + 前端页面 | 前端新增聊天面板，复用现有 WebSocket 连接 |
| 复杂度 | 固定流程 | 简单查询走正则匹配，复杂问句走 AI |

#### 设计

```
                     ┌──────────────────────────────────────────────────────┐
                     │              智能客服 Agent                            │
                     │                                                      │
                     │  用户输入（前端聊天面板）                               │
                     │         │                                            │
                     │         ▼                                            │
                     │  ┌─────────────────┐                                 │
                     │  │   意图分类器      │                                 │
                     │  │  (正则+规则引擎)  │                                 │
                     │  │                  │                                 │
                     │  │  • 查询类：余额/  │  ─── 匹配 → 直接调用 API      │
                     │  │    持仓/成交/订单 │                                 │
                     │  │  • 操作类：下单/  │  ─── 匹配 → 结构化参数          │
                     │  │    撤单          │        → 用户确认 → 调用 API   │
                     │  │  • 复杂类：原因/  │  ─── 不匹配 → AI 增强层        │
                     │  │    分析/策略     │                                 │
                     │  └─────────────────┘                                 │
                     │         │                                            │
                     │         ▼ （仅复杂类）                                │
                     │  ┌─────────────────┐                                 │
                     │  │  AI 增强层       │                                 │
                     │  │  • 语义理解      │                                 │
                     │  │  • 上下文关联     │                                 │
                     │  │  • 结果生成       │                                 │
                     │  └─────────────────┘                                 │
                     │         │                                            │
                     │         ▼                                            │
                     │  ┌─────────────────┐                                 │
                     │  │  操作执行器      │                                 │
                     │  │  → REST API 调用 │                                 │
                     │  │  → 结果格式化    │                                 │

                     │  └─────────────────┘                                 │
                     └──────────────────────────────────────────────────────┘
```

**意图分类规则示例**（纯代码实现，不依赖 AI）：

| 意图 | 匹配模式 | 对应 API | 风险 |
|------|---------|---------|------|
| 查询余额 | `(余额|资金|账户|还有多少钱)` | GET /api/account/info | 无 |
| 查询持仓 | `(持仓|持有|仓位) .{0,10} (600000|浦发|股票)` | GET /api/account/positions | 无 |
| 下单买入 | `(买入|买|购) (?<qty>\d+) 股? (?<symbol>\w+)` | POST /api/orders | 需用户确认 + 风控检查 |
| 下单卖出 | `(卖出|卖|抛) (?<qty>\d+) 股? (?<symbol>\w+)` | POST /api/orders | 同上 |
| 撤单 | `(撤单|取消) (?<orderId>\w+)` | DELETE /api/orders/{orderId} | 需用户确认 |
| 查成交 | `(成交|交易|买到|卖出去了) .{0,10} (600000|浦发)` | GET /api/trades | 无 |

#### 降级路径

| 场景 | 行为 |
|------|------|
| AI 增强层不可用 | 规则引擎覆盖全部查询类意图和 3 种标准下单模式，用户仍可完成 90%+ 的日常操作 |
| 意图置信度低于阈值 | 回复"我没理解您的意思，您可以试试这样说：'查余额'、'买入 100 股 600000'" |
| 下单超出风控限额 | 智能客服调用下单 API 前校验 QuantityValidator，超出则拒绝并说明原因 |
| 非交易时段 | AgentContext 感知阶段，回复"当前为非交易时段，您可以查询但不能下单" |

#### 前端集成

- 在现有 Layout 中新增一个可折叠的聊天面板（独立于现有页面）
- 复用现有 WebSocket 连接，新增 `agent_chat` 通道类型
- 消息记录保存在前端 Zustand store 中，不做持久化

### 4.4 运维诊断 Agent

#### 定位

系统的性能目标（100K TPS，P99 <15ms）和复杂的 CQ 拓扑在发生异常时难以快速定位根因。运维诊断 Agent 提供**延迟分析、堆积检测和诊断建议**能力，帮运维人员理解系统内部状态。

#### 与现有系统的差异对比

| 维度 | 现有系统 | 引入 Agent 后 |
|------|---------|-------------|
| 延迟监控 | 无 | 采集每个 Worker 的批次处理耗时，计算 P50/P90/P99 |
| CQ 堆积检测 | 无 | 监控每条 CQ 的积压事件数，识别瓶颈 CQ |
| 异常模式识别 | 仅日志 | 综合分析延迟、堆积、系统状态，给出诊断结论 |
| 运维建议 | 无 | 根据异常模式给出具体操作建议（扩容/调整参数/重启 Worker） |

#### 设计

```
                     ┌──────────────────────────────────────────────────────┐
                     │              运维诊断 Agent                            │
                     │                                                      │
                     │  数据采集层（定时，每 30 秒）                          │
                     │  ┌────────────────────────────────────────────────┐  │
                     │  │  • Worker Latency：AccountWorker/ME/CW 批次耗时 │  │
                     │  │  • CQ Depth：各 CQ 队列当前积压条数             │  │
                     │  │  • GC Metrics：ZGC 暂停时间、频率                │  │
                     │  │  • SystemStatus + TradingPhase                  │  │
                     │  └────────────────────────────────────────────────┘  │
                     │                      │                                │
                     │                      ▼                                │
                     │  诊断逻辑层（纯代码规则）                              │
                     │  ┌────────────────────────────────────────────────┐  │
                     │  │  规则 1：如果 Worker 批次耗时 > 50ms → P1      │  │
                     │  │  规则 2：如果 CQ 堆积 > 500 条且持续增长 → P1   │  │
                     │  │  规则 3：如果 Worker 耗时 + CQ 堆积同时出现 →   │  │
                     │  │       综合判定为"下游处理瓶颈"                  │  │
                     │  │  规则 4：如果 GC 暂停 > 5ms → P2               │  │
                     │  │  规则 5：多个 P1 同时触发 → P0                  │  │
                     │  └────────────────────────────────────────────────┘  │
                     │                      │                                │
                     │                      ▼                                │
                     │  诊断结果输出                                       │
                     │  ┌────────────────────────────────────────────────┐  │
                     │  │  • 正常：静默                                   │  │
                     │  │  • 异常：推送到前端 Agent 监控面板 + AlertService │  │
                     │  │  • 异常诊断含：问题定位 + 可能原因 + 操作建议     │  │
                     │  └────────────────────────────────────────────────┘  │
                     └──────────────────────────────────────────────────────┘
```

#### 现有系统可复用的数据源

运维诊断 Agent 的数据来源全部来自系统现有组件，不需要新增埋点：

| 数据项 | 现有来源 |
|--------|---------|
| Worker 批次处理耗时 | Worker 自身记录的 batchStart/End 时间（日志中可提取） |
| CQ 队列深度 | QueueManager 的 cqSize() 或 CQ .lastWrittenIndex() - .lastReadIndex() |
| GC 暂停 | ManagementFactory.getGarbageCollectorMXBeans() |
| 系统状态 | LifecycleManager.systemStatus（volatile） |
| 交易阶段 | PhaseManager.currentPhase（volatile） |

#### 降级路径

| 场景 | 行为 |
|------|------|
| 诊断 Agent 自身异常 | 不影响核心交易链路，跳过本次诊断周期 |
| 数据采集失败 | 使用上一次采集值，标记为"stale data" |
| 连续 3 次采集失败 | 告警"运维诊断 Agent 数据采集异常" |

### 4.5 策略回测 Agent

#### 定位

系统运行产生的所有事件都持久化在 CQ 中，天然支持事件重放。策略回测 Agent 利用这一架构特性，提供一个**基于历史事件流的策略模拟环境**，让用户在不影响实时交易的情况下验证策略想法。

#### 与现有系统的差异对比

| 维度 | 现有系统 | 引入 Agent 后 |
|------|---------|-------------|
| 历史数据利用 | CQ + H2 仅用于恢复和查询 | 历史 CQ 事件可直接重放用于策略模拟 |
| 策略验证 | 无策略验证能力 | 支持完整回测，含订单簿重放、虚拟账户结算 |
| 绩效评估 | 无 | 生成多维度绩效报告（收益率、夏普比、最大回撤、胜率、交易频率） |
| 参数优化 | 无 | 回放一次后以不同参数多次重算，辅助参数选择 |

#### 设计

```
                     ┌──────────────────────────────────────────────────────┐
                     │              策略回测 Agent                            │
                     │                                                      │
                     │  用户配置                                             │
                     │  ┌────────────────────────────────────────────────┐  │
                     │  │  • 回测日期范围（如 2026-06-01 ~ 2026-06-20）  │  │
                     │  │  • 标的列表（如 600000, 000001）                │  │
                     │  │  • 策略模板（均线交叉/网格/日内动量等）          │  │
                     │  │  • 策略参数（均线周期/网格间距/止损比例等）      │  │
                     │  │  • 初始资金                                  │  │
                     │  └────────────────────────────────────────────────┘  │
                     │                      │                                │
                     │                      ▼                                │
                     │  回测执行引擎（纯代码，离线运行）                       │
                     │  ┌────────────────────────────────────────────────┐  │
                     │  │  阶段 1：加载历史数据                            │  │
                     │  │  • 读取 matching_output CQ 或 H2 历史成交      │  │
                     │  │  • 重建原始订单簿状态序列（快照点 + 增量事件）   │  │
                     │  │                                                │  │
                     │  │  阶段 2：模拟运行                                │  │
                     │  │  • 按时间序逐笔处理成交/订单事件                 │  │
                     │  │  • 策略规则在每一事件到达时决定是否下单           │  │
                     │  │  • 虚拟账户记录所有操作和资金变动                 │  │
                     │  │                                                │  │
                     │  │  阶段 3：绩效计算                                │  │
                     │  │  • 收益率、夏普比、卡玛比、最大回撤               │  │
                     │  │  • 胜率、盈亏比、平均持仓时间                     │  │
                     │  │  • 交易频率、品种分布                            │  │
                     │  │  • 资金曲线（时间序列输出）                       │  │
                     │  └────────────────────────────────────────────────┘  │
                     │                      │                                │
                     │                      ▼                                │
                     │  回测结果输出                                       │
                     │  ┌────────────────────────────────────────────────┐  │
                     │  │  • 绩效摘要（指标表格）                          │  │
                     │  │  • 资金曲线（时间序列数据，可供前端图表展示）      │  │
                     │  │  • 交易明细（每笔买卖记录）                       │  │
                     │  │  • 回测结果推送至前端 Agent 面板                  │  │
                     │  └────────────────────────────────────────────────┘  │
                     └──────────────────────────────────────────────────────┘
```

#### 使用模式

- **用户触发**：通过前端面板配置参数后发起回测请求
- **异步执行**：回测可能耗时数秒到数十秒，通过 REST API 提交后轮询或 WebSocket 通知结果
- **结果持久化**：回测结果写入 H2 的回测历史表，支持查看历史回测记录和对比

#### 对系统性能的影响

回测 Agent 完全离线运行，使用 H2 和 CQ 归档文件（非当前正在写入的 CQ），对核心交易链路零影响。长时间回测通过 FutureManager 异步执行，不阻塞 HTTP 线程。

### 4.6 交易报告 Agent

#### 定位

系统在 EOD 流程中生成日终报告，但仅在关闭时一次性输出，内容固定。交易报告 Agent 提供**按需生成的多维度交易分析**能力，支持盘中快照和盘后深度分析。

#### 与现有系统的差异对比

| 维度 | 现有系统 | 引入 Agent 后 |
|------|---------|-------------|
| 报告时机 | 仅 EOD 关闭时 | 支持按需生成（日/周/自定义区间） |
| 报告内容 | EOD 流程固定输出 | 可配置分析维度：收益曲线、品种分布、交易频率、持仓周期 |
| 报告分发 | 仅日志 | 推送到前端 Agent 面板，支持对比查看 |
| 数据口径 | 仅当日 | 支持任意日期范围的数据聚合 |

#### 设计

```
                     ┌──────────────────────────────────────────────────────┐
                     │              交易报告 Agent                            │
                     │                                                      │
                     │  触发方式                                           │
                     │  ┌────────────────────────────────────────────────┐  │
                     │  │  • 用户主动请求（前端面板选择日期范围）          │  │
                     │  │  • EOD 自动触发（日终报告增强版）               │  │
                     │  └────────────────────────────────────────────────┘  │
                     │                      │                                │
                     │                      ▼                                │
                     │  数据聚合（H2 只读查询）                               │
                     │  ┌────────────────────────────────────────────────┐  │
                     │  │  SELECT FROM trades WHERE timestamp BETWEEN    │  │
                     │  │  SELECT FROM account_cashflow WHERE ...        │  │
                     │  │  聚合计算：                                      │  │
                     │  │  • 每日 P&L 曲线                                │  │
                     │  │  • 品种盈亏分布                                  │  │
                     │  │  • 多/空盈亏对比                                │  │
                     │  │  • 交易频率热力图（时段×品种）                    │  │
                     │  │  • 持仓周期分布                                  │  │
                     │  └────────────────────────────────────────────────┘  │
                     │                      │                                │
                     │                      ▼                                │
                     │  报告输出                                           │
                     │  ┌────────────────────────────────────────────────┐  │
                     │  │  • 结构化数据（JSON，供前端渲染）                │  │
                     │  │  • 文字摘要                                    │  │
                     │  │  • 推送至前端 Agent 报告面板                    │  │
                     │  └────────────────────────────────────────────────┘  │
                     └──────────────────────────────────────────────────────┘
```

#### 报告维度定义

| 维度 | 数据来源 | 聚合方式 |
|------|---------|---------|
| 每日收益 | H2 trades + account_cashflow | 按日 SUM(amount) |
| 品种盈亏分布 | H2 trades | GROUP BY symbol |
| 多/空盈亏 | H2 trades | GROUP BY side |
| 交易频率 | H2 trades | COUNT(*) / 日 |
| 持仓周期 | H2 trades | 买入 → 卖出时间差 |
| 佣金分布 | H2 trades | SUM(commission) GROUP BY symbol |

## 6. 实施优先级与路线图

| 阶段 | Agent | 前置依赖 | 工作量预估 |
|------|-------|---------|-----------|
| **Phase 1** | 一致性审计 Agent | 无（旁路只读，最安全） | 小 |
| **Phase 1** | 运维诊断 Agent | 无（仅采集已有指标） | 小 |
| **Phase 1** | Agent 公共基础设施（AgentContext、OutputValidator、AgentLogger、AgentWebSocket） | 无 | 中 |
| **Phase 2** | 做市商策略 Agent | AgentWebSocket + REST API | 大 |
| **Phase 2** | 策略回测 Agent | H2 Schema 扩展 | 中-大 |
| **Phase 3** | 智能客服 Agent | AgentWebSocket | 中 |
| **Phase 3** | 交易报告 Agent | H2 查询 | 小-中 |

**建议**：从 Phase 1 开始，三个组件（一致性审计 + 运维诊断 + 公共基础设施）并行推进。它们对现有系统零侵入，且能快速产出可观测的价值——一致性审计是系统承诺的担保，运维诊断是性能目标的保障，公共基础设施是所有后续 Agent 的基础。

## 7. 风险与权衡

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| Agent 误判导致不必要的告警 | 运维疲劳 | 阈值容忍 + 连续两次确认才告警；Agent 自身行为可审计 |
| 智能客服误下单 | 用户资金风险 | 所有下单操作需用户确认 + 风控校验（超出风控限额直接拒绝） |
| 做市商策略异常报价 | 做市商亏损 | 单笔/累计风控限额硬保护，越界自动停止报价 |
| 策略回测结果偏差 | 回测与实盘不一致 | 回测引擎使用与核心系统相同的订单匹配逻辑，回测结果标注"模拟结果，仅供参考" |
| Agent 引入新依赖 | 构建复杂度增加 | 每个 Agent 的依赖独立评估，优先使用项目中已有的依赖（如 Jackson、SLF4J） |
