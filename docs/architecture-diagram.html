HFT Trading System V12

Architecture Diagram · Single JVM · RPO=0

Performance

  • 100K+ TPS sustained throughput
  • HTTP P99 ≤ 5ms sync response
  • E2E P99 ≤ 15ms order to trade
  • Batch 50/100 event processing
  • Snapshot 60s interval
  • ZGC generational, 10G heap
  • Virtual threads for HTTP I/O

Data Storage

  • JVM Heap — primary store (CHM)
  • Chronicle Queue — event streams
  • Chronicle Map — snapshot files only
  • H2 — history queries (off hot path)
  • 3 CQ files — account_input, matching_input, matching_output
  • account_output CQ — WebSocket push
  • account_settlement CQ — loopback

Snapshot Mechanism

  • RPO = 0 zero data loss
  • Event-driven SNAPSHOT event in CQ
  • No pause workers process naturally
  • Atomic rename tmp → .dat
  • MD5 checksum .checksum files
  • 3 snapshot types account, matching, clearing
  • Recovery load snapshot + replay CQ

Thread Model

  • HTTP — N virtual threads (Project Loom)
  • WebSocket — N Netty EventLoop
  • AccountWorker — 1 thread, batch 50
  • MatchingEngine — 1 thread, batch 50
  • ClearingWorker — 1 thread, batch 100
  • MarketDataPublisher — 1 thread
  • SnapshotWorker — 1 timer thread
  • CompletableFuture — HTTP sync wake
  • Three-layer idempotency — tradeId, orderId, position
  • Four-phase recovery — snapshot → CQ replay
